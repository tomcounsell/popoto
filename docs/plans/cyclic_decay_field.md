# CyclicDecayField — Temporal Rhythms + Homeostatic Pressure

## Problem

`DecayingSortedField` (#193) provides monotonic power-law decay — records fade over time unless refreshed. But some records have natural temporal rhythms. A memory about Q1 renewals should resurface every January, not just decay forever. An unresolved action item should build urgency the longer it goes unaddressed.

**Current behavior:**
There is no way to express cyclical relevance or urgency accumulation at the ORM level. Developers must implement cycle detection and urgency tracking in application code and inject it via `computed_sort()`, coupling temporal semantics to every query call site.

**Desired outcome:**
A `CyclicDecayField` that extends `DecayingSortedField` with two additional temporal forces — cyclical resonance and homeostatic pressure — computed atomically in the same Lua script:

```python
class Directive(Model):
    agent_id = KeyField()
    content = Field(type=str)
    relevance = CyclicDecayField(
        decay_rate=0.5,
        cycles=[(TemporalPeriod.QUARTERLY, 5.0, 0)],
        pressure_rate=0.1,
    )

top = Directive.query.filter(agent_id="agent-1").top_by_decay("relevance", n=10)
directive.resolve_pressure("relevance")
```

## Prior Art

- **PR #194**: Lua decay proof-of-concept tests — validated the base decay formula and cmsgpack usage in Lua.
- **PR #190**: `atomic_increment()` — established the Lua scripting pattern with `cmsgpack` + `POPOTO_REDIS_DB.eval()`.
- **PR #195**: Plan for DecayingSortedField — the plan document this plan follows as a template for structure.

## Data Flow

1. **Model definition**: Developer declares `relevance = CyclicDecayField(decay_rate=0.5, cycles=[(period, amp, phase)], pressure_rate=0.1)` on a Model class.
2. **Class creation (metaclass)**: `ModelBase` sees `CyclicDecayField` as a `DecayingSortedField` subclass (which is a `SortedFieldMixin` subclass), registers it in `_meta.sorted_field_names`. The `field_class_key` is `$CyclicDecayF` (auto-generated by `FieldBase` metaclass).
3. **on_save()**: `CyclicDecayField.on_save()` calls parent `DecayingSortedField.on_save()` to store the timestamp in the sorted set. Then stores companion data in two Redis hashes:
   - `$CyclicDecayF:{ModelName}:{field_name}:cycles` — hash mapping member redis_key to msgpack-encoded cycle tuples `[[period, amp, phase], ...]`
   - `$CyclicDecayF:{ModelName}:{field_name}:pressure` — hash mapping member redis_key to msgpack-encoded `{rate, last_resolved}` dict
4. **on_delete()**: Removes member entries from both companion hashes, then delegates to parent `on_delete()`.
5. **top_by_decay(n)**: Same `QueryBuilder.top_by_decay()` interface. The Lua script is extended: after computing base decay, it does two `HGET` calls per member (cycles hash, pressure hash). When both return nil, the overhead is two nil lookups — effectively free. When present, it adds cyclical resonance and pressure to the decay score.
6. **resolve_pressure(field_name)**: Resets `last_resolved` to `time.time()` in the pressure hash for this member. Discharges accumulated urgency.
7. **Output**: Returns model instances ranked by `decay + cyclic + pressure`.

## Architectural Impact

- **New dependencies**: None. Same Redis Lua infrastructure as DecayingSortedField.
- **Interface changes**: Adds `CyclicDecayField` class (new file), adds `TemporalPeriod` constants, adds `resolve_pressure()` method to `Model`. No modifications to existing classes.
- **Coupling**: Low. `CyclicDecayField` subclasses `DecayingSortedField` — no modifications to the parent class. `top_by_decay()` already exists; CyclicDecayField overrides the Lua script used by providing its own extended version. `resolve_pressure()` is a new method on `Model`.
- **Data ownership**: Companion hashes are new Redis keys owned entirely by `CyclicDecayField`. They do not overlap with any existing key patterns.
- **Reversibility**: Fully reversible — new subclass, new method, new constants, no breaking changes.

## Solution

### Key Elements

- **CyclicDecayField**: Subclass of `DecayingSortedField` that adds `cycles` and `pressure_rate` parameters. Manages companion hashes for cycle and pressure data.
- **Extended Lua script**: Computes `decay + cyclic_resonance + pressure` atomically. Short-circuits when companion hashes are empty (pure decay case).
- **TemporalPeriod constants**: Named constants for standard cycle periods in seconds (DAILY, WEEKLY, MONTHLY, QUARTERLY, YEARLY).
- **Model.resolve_pressure()**: Resets pressure for a specific member by updating `last_resolved` in the pressure hash.

### Flow

**Developer defines model** → `CyclicDecayField` registers in `_meta.sorted_field_names` (inherited)

**model.save()** → `on_save()` stores timestamp (parent), then stores cycle/pressure data in companion hashes

**model.touch("field")** → Same as DecayingSortedField (only refreshes decay timestamp)

**query.top_by_decay("field", n)** → Extended Lua script computes three forces → returns top-N

**model.resolve_pressure("field")** → Updates `last_resolved` in pressure hash → discharges urgency

**model.delete()** → `on_delete()` cleans up companion hash entries, then delegates to parent

### Technical Approach

1. **CyclicDecayField class** (`src/popoto/fields/cyclic_decay_field.py`):
   - Subclasses `DecayingSortedField`
   - Constructor accepts `cycles` (list of `(period, amplitude, phase)` tuples, default `[]`) and `pressure_rate` (float, default `0.0`)
   - Validates: `cycles` entries must have positive period and non-negative amplitude; `pressure_rate` must be >= 0
   - `on_save()`: calls parent `on_save()`, then stores cycle and pressure data in companion hashes using `HSET` + msgpack
   - `on_delete()`: removes member from companion hashes, then calls parent `on_delete()`
   - Companion hash keys follow pattern: `$CyclicDecayF:{ModelName}:{field_name}:{partition_values}:cycles` and `:pressure`
   - Embeds extended Lua script as module-level constant

2. **Extended Lua script** (in cyclic_decay_field.py):
   - Same KEYS/ARGV interface as DecayingSortedField, plus two additional KEYS: cycles hash key, pressure hash key
   - KEYS[1] = sorted set key, KEYS[2] = cycles hash key, KEYS[3] = pressure hash key
   - ARGV[1] = now, ARGV[2] = decay_rate, ARGV[3] = max_results, ARGV[4] = base_score_field
   - For each member: compute decay (same as parent), then HGET from cycles hash (if non-nil, decode and compute resonance sum), then HGET from pressure hash (if non-nil, decode and compute pressure)
   - `effective_score = decay + cyclic + pressure`

3. **TemporalPeriod constants** (`src/popoto/fields/constants.py`):
   - `DAILY = 86_400`
   - `WEEKLY = 604_800`
   - `MONTHLY = 2_592_000`
   - `QUARTERLY = 7_776_000`
   - `YEARLY = 31_536_000`
   - Export from `popoto.fields.constants`

4. **QueryBuilder.top_by_decay() override** (in `query.py`):
   - When the field is a `CyclicDecayField`, use the extended Lua script and pass 3 KEYS instead of 1
   - Build companion hash keys from the same partition values
   - Falls back to parent Lua script when field is plain `DecayingSortedField`

5. **Model.resolve_pressure()** (in `base.py`):
   - `resolve_pressure(field_name, pipeline=None)` method on `Model`
   - Validates field is a `CyclicDecayField` with `pressure_rate > 0`
   - Updates `last_resolved` to `time.time()` in the pressure hash via `HSET`
   - Supports optional `pipeline` parameter

6. **Registration** (in `__init__.py`):
   - Export `CyclicDecayField` and `TemporalPeriod`
   - Add to `__all__`

## Rabbit Holes

- **Entrainment / self-correcting cycles**: The roadmap mentions phase and amplitude adjusting based on usage patterns. This is a separate step (future issue) — do not implement cycle self-correction here. CyclicDecayField stores static cycle parameters as configured.
- **ObservationProtocol integration**: Passive behavioral inference (act-on, dismiss, defer) is downstream. CyclicDecayField provides the scoring primitive; observation hooks are a separate issue.
- **Background push-based recall**: The roadmap describes records that surface unprompted via threshold exceeding. This requires a background observer — out of scope. CyclicDecayField only computes scores at query time.
- **Per-member custom cycles**: Tempting to let each member have different cycles at save time. The issue spec defines cycles at the field level (all members share the same cycles). Per-member cycle variation is future work.
- **ZRANGEBYSCORE pre-filtering**: Same optimization deferral as DecayingSortedField. Lua iterates all members.

## Risks

### Risk 1: Lua script complexity with three forces
**Impact:** The extended Lua script does more work per member (two HGET + decode + math). For large sets, this increases latency.
**Mitigation:** When companion hashes return nil (pure decay case), the overhead is two nil HGET lookups — negligible. Benchmark tests for 1K and 10K members will establish baselines. The issue explicitly accepts this tradeoff.

### Risk 2: Companion hash cleanup on delete
**Impact:** If `on_delete()` fails to clean up companion hashes, orphaned entries accumulate.
**Mitigation:** `on_delete()` removes entries from both hashes in the same pipeline as the parent deletion. Test coverage verifies cleanup.

### Risk 3: Cosine overflow in Lua
**Impact:** Very large period values or extreme timestamps could cause floating-point issues in `cos(2 * pi * now / period)`.
**Mitigation:** `now` is seconds since epoch (~1.7 billion), dividing by period (minimum DAILY = 86400) gives a manageable ratio. Lua uses double-precision floats. No overflow risk in practice.

## Race Conditions

### Race 1: Concurrent save() and resolve_pressure()
**Location:** `CyclicDecayField.on_save()` and `Model.resolve_pressure()`
**Trigger:** Thread A calls `model.save()` (which writes pressure data with original `last_resolved`) while Thread B calls `model.resolve_pressure()` (which updates `last_resolved` to now).
**Data prerequisite:** Model must exist in Redis.
**State prerequisite:** Pressure hash must contain the member.
**Mitigation:** Both use `HSET` on the same hash key+field, which is atomic in Redis. The last write wins. If `save()` writes after `resolve_pressure()`, it would overwrite with old `last_resolved` — but `on_save()` should only write pressure data if `pressure_rate > 0` and should read current `last_resolved` rather than overwriting. The implementation should use `HSET` only for `rate` and preserve existing `last_resolved` if already set. Alternative: `on_save()` writes the full pressure struct only on first save (when no existing pressure data exists) and preserves `last_resolved` on subsequent saves.

## Open Questions

1. **Companion hash key pattern with partition_by**: Should companion hashes include partition values in their key (e.g., `$CyclicDecayF:Model:field:partition1:cycles`) to mirror the sorted set partitioning? This seems necessary for correctness — otherwise all partitions share cycle/pressure data for the same member keys. Assuming yes: companion hashes are partitioned identically to the sorted set.

2. **on_save() pressure preservation**: When `model.save()` is called after `resolve_pressure()`, should `on_save()` preserve the existing `last_resolved` value or overwrite it? The safe approach: `on_save()` writes `last_resolved` only on first save (when no existing data); subsequent saves preserve the existing value. This prevents `save()` from accidentally undoing a `resolve_pressure()` call.

3. **Cycles stored per-member or per-field?**: The issue spec defines cycles at the field level (all members share the same cycles parameter). Should the companion hash still store cycle data per-member (for future per-member customization), or should the Lua script read cycles from ARGV (field-level config)? Storing in ARGV is simpler and avoids per-member HGET overhead. Storing in the hash enables future per-member override. Leaning toward ARGV for simplicity with a migration path to per-member later.
